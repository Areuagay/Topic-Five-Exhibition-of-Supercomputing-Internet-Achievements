# 百万核时与万人在线验收分析

分析日期：2026年11月23日。

本文仅分析两个指标：单个案例调用计算资源不少于100万核时，以及平台支撑1万以上用户在线使用。分析依据为本次会话已经完成的项目代码、接口与数据检查，以下测试方法属于建议验收方案；目前没有执行真实百万核时计算或万人压力测试。

## 一、百万核时验收分析

### 1. 指标应该如何理解

“单个案例调用计算资源不低于100万核时”，应按照约定口径，证明该案例实际调用的计算资源达到或超过1,000,000核时。

需要区分三个层级：

| 层级 | 含义 | 与百万核时指标的关系 |
| --- | --- | --- |
| 算子节点 | 工作流中的一次计算、预处理或后处理 | 可以只有少量核时，不要求每个节点都达到百万核时 |
| 一次工作流运行 | 一次提交形成的任务及其子作业 | 是否独立满足百万核时，取决于它是否代表完整验收案例 |
| 验收案例 | 已明确输入、参数、版本、规模和作业范围的一项解算应用 | 按任务书约定逐案例核验，不能用其他案例的资源消耗弥补不足 |

验收前必须确认：一个案例是否允许包含多个批次、是否允许跨运行累计，以及可计入的时间窗。若约定单次工作流达到百万核时，就不能通过多次无关运行累加。

页面中的“运行结束核时”表示计划完成时的目标，“运行消耗核时”表示按当前计量方法得到的已执行量。目标值达到百万，不代表运行消耗量已经达标。

### 2. 当前项目如何体现这个指标

项目运行详情已经显示“运行消耗核时”和“运行结束核时”，运行列表、流程编排、执行监控及节点详情可以查看对应消耗。小数显示已修复，0.22、2.12等接口数值可以保留，而不会直接显示成0或整数。

当前仍有以下实质问题：

| 检查内容 | 当前情况 | 对验收的影响 |
| --- | --- | --- |
| 目标值 | 已配置百万量级的 `target_core_hours` | 能表达计划规模，不能证明已完成规模 |
| 任务执行 | 由本地模拟状态机按时间推进 | 不能代替真实中心的作业执行证据 |
| 资源规模 | 小规模体验直接采用算子登记的CPU等资源 | 未充分表达案例分片、实例数量和中心实际分配规模 |
| 核时累计 | 按节点核数与模拟执行时长计算 | 小规模体验出现零点几或几十核时，在该模型中可以算得通 |
| 历史规划 | 存在按目标值放大CPU、内存和核时的逻辑 | 属于展示推导，不能作为真实资源消耗证明 |
| 数据来源 | 当前解算记录包含 `simulated` 标记 | 正式核验必须区分模拟记录与真实记账 |

例如，本次检查中的地震波体验任务，计算节点采用1核、执行80秒：

```text
1 × 80 ÷ 3600 = 0.0222核时
```

因此，显示约0.02核时符合该小规模模拟模型；但如果把这次已完成体验当作完整百万核时案例，则其执行规模与目标不匹配。修复数字显示只能解决精度问题，不能增加计算规模。

依据：`backend/operator-plan.js`、`backend/experience-store.js`、`frontend/components/run/RunDetailContent.vue`、`frontend/composables/useFormat.ts`、`docs/workflow-execution.md`。

### 3. 核时应该如何统计

建议将“已分配CPU资源核时”与“实际CPU忙碌时间”分开报告，最终以双方确认的指标口径为准。

分配核时的基本计算方法是：

```text
案例核时 = Σ（该案例每条有效资源分配区间的核数 × 区间秒数 ÷ 3600）
```

例如，同一个案例在中心A和中心B分别实际分配16,384核，各运行32小时：

```text
中心A：16,384 × 32 = 524,288核时
中心B：16,384 × 32 = 524,288核时
合计：1,048,576核时
```

该例只是计算说明，前提是资源分配、执行时长、案例归属和结果都能核验。

统计规则需要明确：

1. 不同中心统一“核”的定义，明确物理核、逻辑CPU或认可的等效核口径。
2. GPU、DCU、MLU单独记录卡时；采用等效核时必须有事先确认的折算规则。
3. 核数变化、资源释放、暂停和恢复时分段计量，不能把排队时间当成执行消耗。
4. 失败、取消和重试分别列出，是否计入达标总量按照约定规则处理。
5. 同一资源分配不能因为父作业、子步骤或多套监控系统重复记录而重复累加。
6. 保留原始核秒等精确数据，汇总后再显示小数，不能通过取整或四舍五入跨过验收门槛。
7. 百万网格、百万化合物、百万参数都不是百万核时的计量单位。

### 4. 验收人员如何测试

建议采用“全量原始记账复算＋现场真实抽测”。

| 步骤 | 验收人员的操作 | 需要得到的证据 |
| --- | --- | --- |
| 确定范围 | 固定案例输入、版本、参数、规模、统计窗口和计量规则 | 案例说明和明确的作业范围 |
| 获取记账 | 从各中心调度或正式记账系统独立导出记录 | Job ID、核数、有效时长、状态、来源及导出时间 |
| 核对归属 | 将工作流、函数调用与中心作业逐条对应 | 每条记账确实属于该案例，排除其他项目和重复记录 |
| 独立复算 | 使用独立脚本按约定规则计算全部有效作业 | 逐作业明细、分中心小计、案例总量及排除项 |
| 交叉检查 | 对照日志、资源分配记录和结果文件 | 消耗与执行过程及有效输出相符 |
| 现场抽测 | 提交约定规模的真实任务，观察状态和记账增量 | 平台展示与中心记录可以相互追溯 |

记账至少包含案例标识、运行标识、中心标识、调度作业标识、资源分配唯一标识、尝试次数、核数、有效起止时间、状态及来源。仅凭Job ID不能保证跨中心或跨重试记录唯一。

以Slurm为例，可由中心管理员导出分配级记录，结合 `AllocCPUS`、`ElapsedRaw`、`CPUTimeRAW` 等字段复算。需要区分分配核时和 `TotalCPU` 等使用时间统计，并按现场版本、CPU配置及重排队情况校核。技术字段说明参考Slurm官方 `sacct` 文档：`https://slurm.schedmd.com/sacct.html`。

大规模任务可以提前执行并保存原始材料，验收现场复核和抽测，但这种安排需要提前纳入验收方案。现场小规模抽测本身不能证明百万核时。

建议交付材料包括：案例范围说明、中心原始记账、作业关联清单、复算脚本与明细、执行日志、有效结果，以及现场抽测记录。

通过条件应当是：该案例按约定规则独立复算的有效核时不少于1,000,000，并具备可追溯的真实执行证据。

### 5. 只做模拟时如何评价

模拟可以验证核时计量、资源约束、任务分片、队列和状态流转，但结论只能是“模型中完成了百万核时规模的模拟执行”。

可信的模拟应在开始前固定资源池容量、实例数量、每实例核数、任务规模和虚拟时间规则，再根据分配、执行、暂停、释放等事件累计模拟核时。界面和报告应区分现实时间、虚拟时间、模拟核时及真实核时。

当前体验任务可以继续保留小核时；百万核时模拟应有独立的大规模资源和任务模型。不能在任务完成后，直接根据目标值放大累计数字来替代规模验证。

如果验收要求真实调用100万核时，且没有认可模拟替代，则模拟结果仍不能完成这项真实消耗指标。

## 二、万人在线验收分析

### 1. 指标应该如何理解

“支撑1万以上用户在线使用”需要明确验收的是服务容量，还是实际用户覆盖规模。

| 指标 | 证明内容 | 不能直接替代的指标 |
| --- | --- | --- |
| 注册账号数 | 已建立多少账号 | 同时在线容量 |
| 累计访问人数 | 历史触达规模 | 同时在线容量 |
| 登录会话数 | 某时刻存在多少有效会话 | 用户持续开展业务的能力 |
| 活跃去重用户数 | 约定窗口内实际活动的用户规模 | 压力条件下的容量上限 |
| 万人业务压测 | 约定环境和业务模型下的并发服务能力 | 已有一万名真实自然人使用 |

如果目标是容量，建议定义为：至少10,000个独立测试身份，在同一稳定测试窗口内保持有效在线，并持续开展约定业务。如果明确要求严格超过10,000，可约定11,000等更高测试目标。

万人在线不自动等于一万个解算作业同时执行。任务可以排队，但任务受理、查询、权限和结果访问必须保持可靠。

### 2. 当前项目如何体现这个指标

多中心页面把四个中心的 `concurrent_users` 相加。目前仓库配置为3,700、3,300、3,200和0，合计10,200。

同步脚本明确说明：上游未提供在线用户数，当前保留本地预置值。因此，这个数字是演示配置，不能证明当前真实在线人数，也不能证明万人容量已经通过测试。

即便以后中心提供真实在线数，直接相加也可能重复统计同一人在多个中心的活动；中心本身已有的用户，也未必属于本项目的服务用户。

当前模拟后端尚未完整体现统一身份、按用户隔离的任务和数据、服务端心跳、共享会话及多实例一致性。状态主要按领域保存在进程内，并同步写入JSON文件。这些机制在混合读写负载下需要专项验证。

如果身份、队列和存储由外部主平台承担，压测应覆盖实际完整链路，并说明各模块承担的职责。

依据：`frontend/pages/multicenter/index.vue`、`mock-data/multicenter/clusters.json`、`scripts/sync-multicenter-backend.mjs`、`backend/server.js`、`backend/experience-store.js`。

### 3. 在线人数应该如何统计

建议由服务端根据认证身份、会话有效性和活动记录统计，不接受客户端直接上报人数。

可以约定滚动活跃窗口，例如最近60秒内有有效心跳或业务操作的用户，按统一用户ID去重。60秒只是建议值，应根据业务确定。

统计时需要处理：

- 同一用户的多标签页、多终端和多中心活动合并计数。
- 会话过期、掉线和停止活动的用户按约定时间移出活跃统计。
- 压测身份使用各自会话和授权数据，避免万人共享一个Token。
- 当前活跃人数与历史压测能力分别展示，不能混成一个数字。

当前人数少于万人，不代表平台容量不达标；人数卡片显示超过万人，也不能代替容量测试报告。

### 4. 验收人员如何开展压测

使用正式构建和目标部署环境，记录服务器、实例、网络、数据库、缓存、队列及版本配置。流量经过真实入口和实际业务接口，同时检查压测端自身是否达到计划负载。

建议先固定业务模型。以下比例仅为讨论起点，属于同时用户活动分组，不是请求比例：

| 用户活动 | 建议用户占比 | 主要验证内容 |
| --- | --- | --- |
| 浏览案例、算子和列表 | 40% | 页面与查询可用，分页和筛选正确 |
| 监控任务 | 35% | 各自任务的状态、进度、指标和日志可查询 |
| 数据准备和提交 | 15% | 上传、校验、可靠受理和任务唯一性 |
| 查看和获取结果 | 10% | 结果预览、下载权限和文件完整性 |

请求频率、思考时间、文件大小、轮询周期和任务到达率还需要单独规定。成功判定应检查业务内容、权限和持久化结果，而不只是HTTP 200。

当前运行详情每轮查询5个接口，完成后等待1.3秒再刷新。接口耗时较小时，10,000人同时监控的近似请求率为：

```text
10,000 × 5 ÷ 1.3 ≈ 38,462请求/秒
```

这是根据现有前端行为的估算，不是实测吞吐量。实际周期还包含响应耗时；当响应变慢时，请求率可能下降，因此需要同时观察用户数、实际请求率和响应时间，必要时另加固定到达率测试。技术模型可参考Grafana k6官方说明：`https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/`。

建议测试流程：

1. 小流量验证脚本、身份、数据及业务断言。
2. 按1,000、3,000、5,000、8,000、10,000用户逐级增加负载。
3. 在目标并发下稳定运行60分钟；严格超过万人的目标按约定调整。
4. 分别测试集中登录、提交突发和约定的服务故障恢复。
5. 测试后核对任务、文件和日志完整性，检查队列、连接和资源是否恢复。

HTTP层承担主要并发压力测试，同时使用少量真实浏览器验证页面交互与渲染，不需要在一台电脑上打开一万个浏览器。

### 5. 建议的验收判据和材料

以下时长和性能门槛属于建议值，需要事先确认，并非任务书已经规定的要求：

| 检查项 | 建议判据 |
| --- | --- |
| 有效在线用户 | 稳态约定采样点均达到目标，失效会话不虚计 |
| 稳定时长 | 目标并发下持续60分钟 |
| 业务成功率 | 不低于99.9%，包含内容、权限和持久化检查 |
| 交互类接口延迟 | p95不超过2秒、p99不超过5秒；文件传输和长解算另设指标 |
| 任务受理 | 在约定时限内可靠入队，可追踪且没有任务丢失或重复执行 |
| 用户隔离 | 不发生越权、串用户或错误结果关联 |
| 系统稳定性 | 不出现持续内存增长、不可恢复积压或服务崩溃 |
| 负载真实性 | 压测端实际达到计划用户数和约定操作频率 |

建议交付压测脚本、身份与数据准备说明、部署配置、版本、原始结果、在线人数曲线、请求率、分位延迟、业务错误、系统资源、队列及恢复曲线，以及业务完整性核对记录。

压测报告只能证明对应环境、版本和负载模型下的能力，不能直接外推到其他部署条件。如果还要求实际服务过一万名真实用户，则需要另外提供脱敏账号和活跃记录。

### 6. 使用模拟解算后端时如何评价

解算采用模拟，不妨碍对真实运行的平台开展万人业务压测。可以验证入口、会话、查询、受理、监控及下载等服务能力，但应明确测试中的模拟环节。

如果真实中心调度、鉴权或结果存储未进入测试链路，测试结论应限定为已覆盖的系统范围，不能自动扩展为完整真实解算链路的万人容量证明。

当前10,200人的预置值只能用于演示；要形成万人在线的验收依据，需要实际并发测试及可复核报告。
